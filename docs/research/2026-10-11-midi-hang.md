# The MIDI-parser hang (maps3 finding 2)

Investigated 2026-10-10 and 2026-10-11, on a private Xvfb `:92`, using scratch builds in `/tmp/claude-1000/vmidi/`. The problem is
finding 2 of `docs/playtest-2026-10-10-maps3.md`:

- With music on, the game froze twice, each time just after `Doing a MIDI transition! trans: 9`.
- The audio thread was spinning inside `MidiParser` while it held the mixer mutex.
- The main thread was blocked in `playSFX`.

## Verdicts

| Question | Answer |
|---|---|
| Root cause | **A data race in `Ultima8::MidiPlayer`, which is unmodified upstream code.** The audio thread drives both XMIDI parsers from the OPL timer, inside the mixer callback and with the mixer mutex held. The game thread resets the same parsers through `stop()`, `playTransition()`, `play()` and `load()`, and it takes **no lock** to do so (`midi_player.cpp:138-195`, `245-259`). Suppose the reset lands while `MidiParser::onTimer` is walking a freshly started track's tick-0 events. The parser is then left re-sending one stale delta-0 event forever (`midiparser.cpp:230-296`, `365`). The next mixer call from the game thread blocks for good. |
| Is track 9 missing or empty? | **No.** The transition XMIDI has 10 tracks, and 9 is a valid one. Every dump shows `_numTracks 10` and a valid `_activeTrack`. `_playPos == 0` is not "no data". It is what `stopPlaying()` → `resetTracking()` leaves behind (`midiparser.cpp:539-544`, `462-464`, `midiparser.h:94`). |
| Which parser? | **Either one.** The API stress hung the transition parser 6 times out of 6, matching the field dump. The organic combat-toggle stress hung the main music parser twice. |
| Reproduced on purpose | **Yes.** API stress: stock hung in **6 of 6** valid runs, each within ≤6000 iterations. Organic combat toggling (the field's path): stock hung in **2 of 5** runs, over 14,368 toggles. Every hang has the field's signature: the audio thread is in the `MidiParser::onTimer` loop, the main thread waits on the mixer mutex, `_playPos` is null, and every `_position` field is zero. |
| Fix | **A `Common::Mutex` in `Ultima8::MidiPlayer`.** It is taken in `onTimer()` and in every method that touches a parser. This is the same pattern as the generic `Audio::MidiPlayer` (`audio/midiplayer.cpp:150`). The fix is in `engines/` only: **2 files, +35/−7** (`git apply --numstat`), diff below and in `/tmp/claude-1000/vmidi/fix.diff`. |

## 1. Root cause

### The two threads

- **Audio thread.**
  - `MixerImpl::mixCallback` takes the mixer mutex (`audio/mixer.cpp:331-334`).
  - The OPL emulator's `EmulatedChip::readBuffer` fires the driver timer while it generates samples (`audio/chip.cpp:126-127`).
  - The chain is `MidiDriver_Multisource::onTimer` (`audio/mididrv_ms.cpp:392-397`) → `Ultima8::MidiPlayer::onTimer` (`midi_player.cpp:245-259`) → `_parser->onTimer()` (247) and `_transitionParser->onTimer()` (249).
- **Game thread.** `U8MusicProcess` calls the same parsers directly, and nothing in `midi_player.cpp` takes a lock:
  - `playTransition()` runs `_parser->stopPlaying()` (169-170), `_transitionParser->setTrack()` (179) and `startPlaying()` (184).
  - `stop()` runs `stopPlaying()` on both parsers (188-195).
  - `play()` runs `_transitionParser->stopPlaying()` (158-161).
  - `load()` deletes `_parser` (95-99).

### The trigger path

- `MainActor::setInCombat` and `clearInCombat` (`main_actor.cpp:550-560`) call `playCombatMusic(98)` and `restoreMusic()` (`u8_music_process.cpp:77-100`).
- If music is playing, `playMusic_internal` starts a transition: the `warning` and `playTransition()` at `u8_music_process.cpp:184-186`.
- The next toggle arrives while `_state != PLAYBACK_NORMAL`. It sets `PLAYBACK_PLAY_WANTED` (150-152), and the next `run()` calls `_midiPlayer->stop()` (211-213).
- Every combat-mode mouse run toggles (`u8_avatar_mover_process.cpp:238-239`, `272-273`, `311-312`). That is why maps3 logged 566 transitions, every one of them `trans: 9 overlay: 0` (`grep -o "trans: [0-9]* overlay: [01]" /tmp/claude-1000/vmaps3/lv_run.log | sort | uniq -c`).

### Why a reset livelocks the parser

`stopPlaying()` → `resetTracking()` → `Tracker::clear()` zeroes `_position` and nulls every `_playPos`. It does **not** clear `_nextSubtrackEvents` (only `setTrack` and `startPlaying` do, at `midiparser.cpp:522-524` and `550-552`). Now suppose the audio thread is inside the `while (!_abortParse)` loop (`midiparser.cpp:230`) at that moment. Then:

1. `eventTick = _subtracks[0]._lastEventTick (0) + info.delta`, and `eventTime = 0 + (eventTick − 0) × _psecPerTick` (234-235).
2. The stale event has `delta 0`, so `eventTime = 0`. `endTime` was computed before the reset (209) as `0 + _timerRate = 4000`. So `eventTime > endTime` (253) never holds.
3. `processEvent` re-sends the event to the driver (275) and returns true, because it is not End-of-Track.
4. The times are written back as 0 (283-289). `isTracking(0)` is false, so nothing advances `_playPos` (291-293).
5. `determineNextEvent()` (294) finds no tracking subtrack and falls back to subtrack 0 (365). That is the same stale event.

Nothing on the audio side ends the loop. Inside it, `_abortParse` is set only by the loop-section jump (248, unused by U8) and by End-of-Track handling. A stale non-EOT event reaches neither. From outside, only the game thread can rescue the parser, through `setTrack`, `unloadMusic` (732) or `jumpToTick` (719). But the game thread blocks on the mixer mutex at its next mixer call (`playSFX` → `isSoundHandleActive`, `mixer.cpp:593-594`), so the parser is never rescued.

- **Why tick 0.** XMIDI tracks open with a cluster of delta-0 meta and controller events: tempo `0x51`, time signature `0x58`, key signature `0x59`, controller `B5 07`. The dumps show exactly those as the stale event. With a nonzero delta, the loop would re-send a few events and then exit.
- **Why each sample lands somewhere different.** The field's `midiparser.cpp:356` is the `for` loop in `determineNextEvent`, called from line 294 of the same loop. My samples landed on 235/237/258/275/419/422 and inside the AdLib driver. All of them are the same loop.

### Two side effects of the same race

These were not observed, but they follow from the code [INFERENCE]:

- `load()` deletes `_parser` while the audio thread may be inside `_parser->onTimer()`. That is a use-after-free.
- `setTrack()` racing `onTimer` can leave a parser silently stopped.

The fix closes both.

### Why `music_driver=null` never hung [INFERENCE]

That path uses `MidiDriver_NULL_Multisource`. Its timer runs on the SDL timer thread, not inside the mixer callback. A spin there would hold no lock that the game thread takes every frame, so the game would not freeze. Not tested.

## 2. Reproduction

### Builds

All three binaries come from a copy of `scummvm-lv/` (built 2026-10-10 19:22). Its `engines/ultima` sources match `scummvm-lv-console` HEAD `8af4f74e`, except the generated `detection_tables.h` (`diff -rq`), and its `audio/midiparser.cpp` is identical.

- `scummvm-stock-harness` (md5 `7e1d9eb7…`): stock, plus the scratch harness.
- `scummvm-fix-harness` (`68e57d1f…`): the fix, plus the harness.
- `scummvm-fix` (`97d449b3…`): the fix only.

`disassemble MidiPlayer::onTimer` shows 0 `StackLock` calls in stock and 2 in the fixed binaries.

### Harness (`/tmp/claude-1000/vmidi/harness.diff`, scratch only, not part of the fix)

It adds a console command `MidiStress` and runs one tick of it per pass of `Ultima8Engine::runGame`:

- **`api <n> <perFrame> <maxSpin>`.** Each iteration runs `playTransition(rnd 0..9, rnd overlay)`, then a random busy-wait, then `stop()`. That is the call pair `U8MusicProcess` makes (`playMusic_internal`, then `run()` PLAY_WANTED).
- **`combat <n> <every>`.** It toggles `MainActor::setInCombat` / `clearInCombat` every `<every>` passes. That is the real `playCombatMusic(98)` / `restoreMusic()` path through `U8MusicProcess`. It also logs the TrackState and `isPlaying` before each toggle.
- **Both modes** then take the mixer mutex (`isSoundHandleActive`), as `playSFX` does. So a stuck audio thread freezes the game exactly as the field hang did.

### Setup

- The ini is the maps3 ini without `music_driver=null`. It keeps `mute=true`, `music_volume=0` and `SDL_AUDIODRIVER=dummy`. The driver is auto-detected, and the backtraces show `MidiDriver_Miles_AdLib` + DOSBox OPL.
- The save is `run-s4-columns-done.sav` on Map 11, whose track is 48 (md5 `cc6ed3a1…`, unchanged at the end).
- gdb launched the game as a child, because `ptrace_scope=1` refuses attach.
- **Hang detection.** No progress line for 30 s triggers a SIGINT, then a python dump (`dump.py`) of every thread and the parser state, then `continue`. A second sample follows 6 s later.

### Lock order

- **The audio thread** takes the mixer mutex, then `MidiPlayer::_mutex`, then any driver leaf locks.
- **The game thread** takes `_mutex`, then the driver leaf locks:
  - `MidiDriver_Multisource::_fadingMutex`, used by `isFading` / `abortFade`. `updateFading` releases it *before* calling the timer proc (`mididrv_ms.cpp:163`, `392-397`).
  - The OPL register writes, which take no mixer lock.

Nothing takes the mixer mutex while holding `_mutex`, so there is no ABBA. The one exception would be `_driver->close()` (OPL `stop()` → `mixer->stopHandle`), and the destructor therefore runs it outside the lock. `Common::Mutex` is recursive, but no `MidiPlayer` method re-enters another anyway.

### Left unlocked on purpose

- `startFadeOut`, `isFading` and `syncSoundSettings` touch only the driver, and the driver already locks its fade state.
- `getSequenceCallbackData` is a single byte read.

## 5. The `audio/` bug, for upstream

`MidiParser` is not thread-safe, and `Audio::MidiPlayer` serialises it correctly (`audio/midiplayer.cpp:76`, `150`, `162`). `engines/ultima/ultima8/audio/midi_player.cpp` does not, on upstream `master` either, so the diff above is upstreamable as-is.

`MidiParser::onTimer` also turns any lost tracker state into a livelock instead of a stop:

- `determineNextEvent()` falls back to subtrack 0 when no subtrack is tracking (`midiparser.cpp:365`).
- The loop then re-dispatches that stale event with no exit unless time advances (230-296).

A defensive guard at the top of the loop would make the same misuse fail quietly instead of hanging the mixer: `if (!_position.isTracking()) break;`, or stop when `_nextEvent`'s subtrack is not tracking. I have neither applied nor tested it; it is a suggestion for an upstream report.
